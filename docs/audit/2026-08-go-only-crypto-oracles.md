# Go-only crypto: what actually grades it

**Date:** 2026-08-17 · **Scope:** the EVM/STARK proof-system primitives that ship
Stack-IR codegen in the Go tier only.

## The problem this document answers

Rúnar's headline correctness invariant is seven-tier byte parity: seven
independently written compilers must emit identical Stack IR and identical
Script hex. For BabyBear, KoalaBear, Poseidon2, BN254/Groth16, Merkle and the
SP1 FRI verifier that invariant is **definitionally vacuous** — those families
ship in one tier by project policy, and one implementation cannot disagree with
itself. Their fixtures carry `"compilers": ["go"]`, so the parity runner has
nothing to compare.

Everything that grades them therefore reduces to `tests/vectors/*.json` (22
files) plus the SP1 fixtures under `tests/vectors/sp1/`. This document says, per
family, exactly what those vectors are worth.

## Classification

Categories, as posed by the audit:

- **(a)** an official upstream KAT — a value published by the upstream project or
  standard, not computed here;
- **(b)** vectors generated by an independent second implementation;
- **(c)** nothing but a self-produced golden.

| Family | Reference actually used | Category | Reproducible? |
|---|---|---|---|
| BabyBear base field (add/sub/mul/inv) | Plonky3 `p3-baby-bear` 0.5.2 | **(b)** | yes — byte-for-byte |
| BabyBear ext4 (mul/inv) | Plonky3 `p3-field::BinomialExtensionField` | **(b)** | yes |
| KoalaBear base field | Plonky3 `p3-koala-bear` 0.5.2 | **(b)** | yes |
| KoalaBear ext4 | Plonky3 `p3-field::BinomialExtensionField` | **(b)** | yes |
| Poseidon2 (KoalaBear, width 16) | Plonky3 `default_koalabear_poseidon2_16` driven through `p3_symmetric::Permutation` | **(b)** | yes |
| BN254 field arithmetic + G1 | gnark-crypto `bn254` `fp` / `G1Affine` | **(b)** | yes |
| BN254 pairing | gnark-crypto `bn254.Pair` | **(b)**, plus algebraic invariants | yes |
| Merkle (SHA-256 tree) | `sha2` crate for the hash; **tree shape written in the generator** | **(b)** for the hash, **(c)** for the scheme | yes |
| FRI colinearity | Plonky3 field arithmetic; **folding equation written in the generator** | **(b)** for the arithmetic, **(c)** for the vectors — but the rule itself is anchored by the `minimal-guest` proof (see below) | yes |
| SP1 FRI proof fixtures | real Plonky3 output (`minimal-guest`, `evm-guest`) plus seven derived corruptions | **(a)** for the positive proofs, **(b)** for the rejection corpus | not in CI |
| SP1 Groth16 verifying key (v6.0.0) | SP1's own `Groth16Verifier.sol` | **(a)**, but not reproducible in CI | no |

**No family in this set has an official upstream KAT for its arithmetic.** The
strongest grade available anywhere here is (b). Where a category-(a) artifact
does exist — the SP1 proof fixtures and verifying key — it is an upstream
*artifact*, not a published known-answer vector, and it is not regenerable in CI.

### Where (b) is genuinely (b)

For BabyBear, KoalaBear, Poseidon2, BN254 field/G1 and BN254 pairing, the
generator calls the upstream library to compute the answer. It does not
re-implement the operation and then check it. Poseidon2 in particular runs the
real `p3_koala_bear` permutation through the `Permutation` trait, so a wrong
round constant or a wrong S-box degree in the Rúnar codegen shows up as a wrong
digest.

### Where (b) quietly becomes (c)

Two families look like (b) and are not, in the part that matters:

- **Merkle.** The generator uses `sha2` for the compression function, but the
  *tree* — leaf/node domain separation, ordering, odd-node handling — is written
  in `generate_merkle_vectors.rs`. There is no upstream to be right against,
  because the SHA-256 outer layer is a deliberate Rúnar design decision
  (`tests/DECISION-MERKLE-HASH.md`, choosing SHA-256 over SP1's native
  Poseidon2 because BSV has `OP_SHA256`). So the vectors prove the Script
  implementation matches a Rust implementation of the same repo-authored scheme.
  If the scheme itself diverges from what the proof-format adapter produces, both
  sides agree and both are wrong.
- **FRI colinearity.** The generator uses Plonky3 field arithmetic but codes the
  folding relation `g(x²) = (f(x)+f(−x))/2 + α·(f(x)−f(−x))/(2x)` by hand. It
  does **not** call `p3-fri`. For the standalone colinearity VECTORS the risk is
  the same shape as Merkle's: the arithmetic is independent, the rule is not.

  The folding rule as a whole is a different matter, and it is measured rather
  than argued. `tests/vectors/sp1/fri/minimal-guest/proof.postcard` is real
  Plonky3 output — a Fibonacci AIR proven over KoalaBear by `regen/`, which
  depends on Plonky3 proper — and `packages/runar-go/sp1fri` is an independent
  Go reimplementation that accepts it end to end. That acceptance is a
  cross-implementation check: perturb `foldRow` to take
  `KbTwoAdicGenerator(logHeight)` instead of `logHeight + logArity` and
  `TestVerifyMinimalGuest` fails with `query 0 final_poly mismatch`. A verifier
  that folded differently from Plonky3 could not verify a Plonky3 proof.

This is the "seven-tier agreement proves agreement, not correctness" lesson
applied one level down — here it is *two*-implementation agreement, and the two
implementations share an author and a spec.

## What was verified on 2026-08-17

- **All 22 vector files reproduce byte-for-byte.** Every generator was re-run
  (`cargo build --release` + the five Rust binaries, and `GOWORK=off go run .`
  for BN254) and `git diff -- tests/vectors` came back empty. This is now
  enforced by `tests/generate-vectors/verify-reproducible.sh` and a CI job, so
  "derived from Plonky3" is a check rather than a comment.
- **BN254 pairing widened 4 → 34 vectors** and given its first consumer.

## The BN254 pairing gap, and what was done about it

`bn254_pairing.json` carried **4 vectors** for the single most security-critical
operation in the Groth16 path. Worse than the count: it was the **only file
under `tests/vectors/` with zero consumers**. Nothing in the repo read it, so
those four vectors were never executed by any test — a grep across Go, TS, Rust,
Python, Zig and Ruby finds the filename only in the generator that writes it.

There is no upstream KAT for the pairing here and no second pairing
implementation available offline, so more randomly-sampled vectors from the same
gnark-crypto call would not add an independent grade. The corpus was instead
rebuilt so it can be **falsified by algebra over the recorded values**:

- **Bilinearity.** `e(a·G1, b·G2) = e(G1, G2)^(a·b)`, so the result depends only
  on `a·b mod r`. Six classes, each holding every spelling of one product —
  scalar on G1, scalar on G2, each non-trivial factorisation, and an `(r+2)`
  case that must reduce into the `k=2` class — and every member must carry a
  byte-identical `expected_gt`. A pairing that is not bilinear cannot produce a
  self-consistent file.
- **Degeneracy.** 7 vectors that must equal the Fp12 identity: `e(O, G2)`,
  `e(G1, O)`, the two-term `e(a·G1, G2)·e(−G1, a·G2)` for several `a`, and the
  full four-term Groth16 shape
  `e(A,B)·e(−α,β)·e(−C,δ)·e(−vk_x,γ) = 1`.
- **Non-degeneracy.** 4 negative controls that must **not** be the identity,
  including the four-term product with `A` off by one generator. Without these,
  "return 1 for everything" satisfies every positive vector.

`conformance/scripts/check-bn254-pairing-invariants.mjs` enforces all of that
plus field-element canonicity (`< p`) and a coverage floor, and ships an
8-scenario self-test that shows each invariant rejecting a corrupted corpus.

## Residual risk — what is still not graded

1. **The Merkle scheme is graded against itself.** Independent field arithmetic,
   repo-authored tree shape. An error in the *scheme* is invisible to these
   vectors. Closing it needs a fixture produced by SP1's own proof-format
   adapter, not by `tests/generate-vectors/`.

   The FRI folding rule used to be listed here too. It no longer belongs: the
   `minimal-guest` fixture is real Plonky3 output and the independent Go
   verifier accepts it end to end, so a fold that diverged from Plonky3 would
   fail (demonstrated — see the FRI colinearity note above). What remains
   ungraded is narrower and was not previously written down: the pinned config
   sets `max_log_arity: 1`, so every fold is arity-2 and
   `reverseSliceIndexBits` is a no-op on two elements. Deleting that call leaves
   every SP1 FRI test passing. The bit-reversal is unexercised until a fixture
   with `max_log_arity > 1` lands.
2. **The SP1 FRI negative corpus is seven of eight, and the eighth is
   impossible at this parameter set.** `bad_merkle`, `bad_folding`,
   `bad_final_poly`, `wrong_public_values`, `wrong_program`, `truncated` and
   `all_zeros` carry real bytes generated by
   `tests/vectors/sp1/fri/corruptions/gen.go`, and
   `compilers/go/codegen/sp1_fri_negative_test.go` drives each through the
   reference verifier asserting both THAT it is rejected and WHERE — including,
   for several, that the real detection point differs from the one the original
   corruption matrix predicted.

   `bad_vk` has no fixture and cannot have one yet: `minimal-guest` is a raw
   Plonky3 `p3_uni_stark::Proof` with no SP1 wrapper, so there is no verifying
   key to corrupt, which is why `SP1VKeyHashByteSize` is pinned to 0. Inert
   bytes no test could assert on would be worse than the absence; the
   directory's README sets out what would have to land first, and
   `TestSp1FriVerifier_BadVkCorruptionIsDocumentedAbsent` holds that reasoning
   to the tree.

   `tests/r220-sp1-fri-negative-corpus.test.ts` pins this section to the
   filesystem so it cannot drift back out of date.
3. **The SP1 Groth16 verifying key is not reproducible.** `tests/vectors/sp1/v6.0.0/vk.json`
   records `source: /Users/<user>/.sp1/circuits/groth16/v6.0.0/Groth16Verifier.sol`
   — a path on one developer's machine. The values are upstream SP1's, but
   nothing in CI can re-derive them, and nothing detects a hand-edit.
4. **Coverage holes in which tier consumes which vector file.** Two vector files
   are consumed only by TypeScript tests even though the codegen they grade is
   Go-only:
   - `merkle_rejection.json` — consumed only by `tests/merkle-vectors.test.ts`.
     The Go tier gets `merkle_inclusion.json` but no rejection vectors.
   - `babybear_ext4_mul.json` — consumed only by `tests/babybear-ext4-vectors.test.ts`.
     (`babybear_ext4_inv.json` does reach `compilers/go/codegen/script_correctness_test.go`.)
5. **Upstream correctness is assumed.** Plonky3 and gnark-crypto are taken as
   ground truth. That is a reasonable assumption and it is still an assumption.

## Rules going forward

- `tests/vectors/*.json` is now inside the golden-provenance gate's matchers. A
  change there needs a content-pinned, reviewed allowlist entry — a silent
  regeneration in this directory is strictly more dangerous than one under
  `conformance/tests/`, because no second tier would ever contradict it.
- If regenerating moves a byte, do not commit the new bytes as a fix. Either an
  upstream dependency changed (pin the reason, allowlist each moved file) or a
  vector was hand-edited (revert it).
